# 架构与数据边界

VoxWeave 的唯一业务入口是本机后台服务。QML 桌面端、`voxweave` CLI 和第三方自动化都只提交 `voxweave-control v1` 请求，不直接扫描模型、写任务库或调用 RVC。

```text
QML desktop ─┐
CLI/AI ──────┼─ authenticated loopback API ─ Controller（只组装与管理生命周期）
HTTP client ─┘                                  │
                                         OperationRouter
                         ┌──────────────────────┴──────────────────────┐
              serialized offline task worker             realtime session manager
                         │                                           │
        FFmpeg / analysis / official RVC adapter      resident RVC + PortAudio stream
                         │                                           │
              validated media + provenance              microphone → changed playback
                         └──────────────────────┬──────────────────────┘
                                  repositories / artifact store
                                               │
                                             SQLite
```

## 服务发现

服务只监听 `127.0.0.1` 的随机端口。独占进程锁成功后才写发现文件，内容包括 PID、端口、协议、版本、启动时间和随机令牌。客户端先验证 PID 存活，再用令牌请求 `/v1/handshake`；任一步失败都不会沿用该发现文件。令牌随服务进程更换。

## 持久状态

数据目录下的 SQLite 是模型、预设、任务、实时会话、事件、批量规则、批量运行、监控内容指纹、产物和归档记录的唯一真源。任务、模型、预设、实时、批量和归档各自通过对应 repository 读写，每个 repository 只查询自己负责的表；跨域信息由领域服务通过公开方法组合，不能穿透到另一个管理器的 repository。领域管理器只在需要跨 repository 原子提交时打开事务，不持有 SQL。设置文件只能由服务进程原子更新，GUI、批量线程和安装任务都通过该边界提交变更。离线任务只有一个工作线程；每次 RVC、分离、模型检查和安装命令都由统一的可取消子进程边界执行。实时会话不是第二个任务系统，而是独立的单会话状态域，因为它需要长期占用麦克风和播放设备。任务管理器和实时管理器共享同一个 GPU 调度闸门：已有离线任务运行时实时启动失败，实时期间的新任务保持 queued，停止后由原工作线程继续。

`Controller` 是组合根，只创建服务、启动和关闭后台组件，并把请求交给 `OperationRouter`。协议操作、同步或长任务处理器以及输入/模型快照准备器只在路由表中绑定一次；路由表启动时必须与协议声明完全一致。模型登记、权重检查、目录扫描、目录服务读取和模型导入分别由 registry、inspector、scanner、catalog client 与 importer 负责，登记层不接触网络、子进程或文件扫描。

任务只有 queued、running、completed、failed、cancelled、interrupted 六种生命周期状态，处理阶段保存在独立字段。任务和 queued 事件、状态和对应事件均在一个事务中提交；服务只在全部处理器注册后恢复队列。提交时会固化输入路径、文件身份与已知内容哈希，以及精确的模型 ID、权重哈希和索引哈希；执行前后再次验证，重试沿用原快照，不会悄悄改用后来替换的文件或模型。内容 SHA-256 每次都从稳定打开的文件句柄直接读取，不把路径、大小或时间戳当作哈希缓存身份；Windows 读取期间拒绝并发写入与替换，读前、读后文件身份不一致会失败。普通运行任务在服务重启后标记为 `interrupted`，不会根据零散临时文件猜测完成度；批量父任务则由持久化的批量运行记录重新汇总子任务状态。用户可以显式重试；已完成产物的清单带最终哈希。批量监控先计算内容 SHA-256，再按批量规则、规范路径和内容哈希去重；大小与修改时间只用于判断文件是否写稳，输出根永远被排除在输入枚举之外。同名不同扩展名和内容已变化的输入会得到不同输出路径，提交失败也会进入批量运行结果而不是被静默忽略。

运行时安装和 URL 模型导入都先进入任务专属 staging，验证成功后才移动到正式目录并更新设置或模型登记；失败内容进入可追溯的 failed 目录，不会伪装成可用组件。媒体输出在目标目录内完成临时写入、完整解码、清单和检查点提交，最后一步才原子发布。

实时会话只有 starting、running、stopping、stopped、failed、interrupted 六种状态。服务先持久化 starting 再启动工作进程；工作进程常驻 RVC 和 Silero VAD 模型，PortAudio 持续读取麦克风。检测到人声或输入电平达到可听范围的音频块交给 RVC，只有 VAD 和电平门都判定为静音的块才跳过推理并向播放设备写入零值。测试模式使用 capture、playback、tail 三阶段状态机：capture 阶段转换并缓存整句但保持播放静音，检测到停顿后进入 playback 顺序输出缓存，队列清空后进入 tail 丢弃播放同期输入和扬声器尾音，最后清空转换与 VAD 状态并恢复 capture；这是会话状态，不参与模型和音频处理器缓存身份。心跳回传语音检测来源、测试阶段、缓存块数、播放和麦克风暂停状态、推理耗时、输入/输出电平和音频中断次数。停止先通过控制管道关闭 PortAudio 流；音频线程在期限内没有退出时，工作进程报告失败并以非零状态退出，不发送 `worker_stopped`，也不复用仍可能活动的处理器。服务重启不会猜测旧音频流仍然存在，而是把遗留活动会话标记为 interrupted。

每个分析样本、预览、转换输出和清单都登记所属任务、路径、类型、哈希与归档状态。中间产物没有自动删除策略。显式归档任务只选择终态任务目录，跨盘时先复制校验，再同步迁移产物记录以及任务参数和结果引用。结构化服务日志位于数据目录 `logs`，按 10 MB、5 个文件轮转；诊断快照由服务从真实运行状态生成。

## 桌面端边界

`Bridge` 只负责组装对象、全局语言、状态和应用生命周期。模型目录、媒体工作区、实时会话、批量规则、任务列表、长任务活动状态和维护工具分别由独立 ViewModel 持有；QML 直接消费这些对象的 `QVariantList`/`QVariantMap`，不传递 JSON 字符串。实时 ViewModel 把页面上的全部实时参数合并成一个配置，通过服务进程原子写入设置文件；设备只保存接口与名称，页面获得新一轮设备枚举后再解析当次编号。任务列表只在启动或用户刷新时分页读取，之后通过带游标重连的 WebSocket 事件按任务 ID 增量更新；实时 ViewModel 在活动会话期间每 250 毫秒读取一次检测与电平状态，其余时间降回一秒。

## 推理边界

VoxWeave 锁定 RVC 上游提交 `4338f12c3c28c80b3ac015e2d0df66c41592746d`。`rvc_worker.py` 是 VoxWeave 自己维护的窄适配器，只调用该提交的官方配置与 VC 模块。模型检查在 RVC Python 子进程中显式执行 `torch.load(..., weights_only=True)`；不安全或结构不兼容的权重不会进入 ready 状态。

媒体唯一生产链是：FFprobe 检查、FFmpeg 提取、按内容模式分析、可选人声分离、可选说话人选择、RVC、采样长度对齐与边界淡化、响度匹配、封装、完整解码。代码按检查点/发布、媒体输入输出、分析/分段、转换编排四个单向依赖层组织。超过 90 秒的整轨会在低能量位置切成约 45 秒的块，由同一个已加载模型的 RVC 子进程批量处理，再按原采样位置重组；这避免 RMVPE 对超长输入的 cuDNN 限制，也避免每块重复加载权重。视频映射并复制所有原始流，再添加命名后的变声音轨；不会用重编码后的视频冒充“复制原流”。

实时生产链使用锁定 RVC 上游的 `infer.rtrvc.RVC` 和固定版本的 Silero VAD，两者都在子进程内常驻。工作进程只负责验证设备与模型并组装运行对象；采样率协商、VAD 状态、音频缓冲和推理、SOLA 拼接、PortAudio 流生命周期分别位于独立边界。Windows 设备枚举以 WASAPI 的默认输入和输出为首选，只有该接口不能组成完整路由时才回退。麦克风优先以单通道打开；设备只接受多通道输入时选择电平最高的通道，不做可能抵消阵列信号的通道平均。一条 16 kHz CPU 支路按 512 个采样点持续判断语音，连续两个语音窗口才打开推理，句尾保留 250 毫秒收束；同时以用户设置的输入电平门兜底 VAD 漏检。普通模式和测试模式只使用这一个 RMS 电平门，旧的固定电平与固定峰值门限都不存在。音频上下文始终推进，但只有打开的块完成 F0、检索和 RVC 推理，再重采样到设备采样率并用 SOLA 搜索与交叉淡化拼接；关闭的块直接输出零值并清空旧的拼接和音高缓存。0.25、0.5 和 1.0 秒三档共享同一实现；较长块不会改变算法，只扩大实时预算并增加可预期延迟。

## 跨平台边界

路径使用 `pathlib`，服务和数据库没有 Windows 专用格式；启动脚本同时提供 PowerShell 和 POSIX 版本。进程存活、可执行文件位置和 Qt 部署由平台适配层处理。0.1 只把 Windows CUDA 写为已验收，未获得对应机器前不宣称 macOS/Linux 可用。
